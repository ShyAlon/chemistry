# Review recording, impact preview and the local gate

Four small tools, each from a real failure while landing G13-G15. None of them changes CI or its cost.

## `scripts/record-review.mjs`: record a finished review
Computes the review bindings (source, lesson content, unit map, figures) with the checker's own functions and replaces only the `semanticReview` block. It needs the reviewer's own id and the all-admin pages the reviewer actually viewed (`--admin-pages 1,36` or `none`). It stops if the id is missing, a placeholder or an author, if the pages do not match the map's all-admin pages, if figure binding fails, or if the file layout is not reproducible (it never reformats a map). Without `--write` it prints the exact diff. It cannot decide that a review happened or that the science is complete; the independent reviewer's report is the evidence, and the tool never fills an attestation for them.

## `scripts/review-impact.mjs`: what will my change invalidate?
`node scripts/review-impact.mjs [--base origin/main]` lists changed files, predicts which recorded reviews they invalidate (figure closure of the course, topic content, unit map file) and then prints the checker's real verdict. A style change in a figure-bound root such as `src/style.css` fails every reviewed GC2 topic; the preview says so before a commit. Counts are topics (one review record per topic). The prediction is conservative and limited: it follows the figure closure (static relative imports plus the policy's extra files), the topic JSON and the unit map file. Courses without a `figureBinding` use the older two-file fallback (`figures.jsx`, `figures-nuclear.jsx`), so an edit elsewhere may not be predicted there. The checker verdict printed under the prediction is the authority.

Note: `package.json` is a bound extra file of the GC2 figure closure, so any change to it (even adding a script) invalidates those reviews. That is why there is no `npm run gate` alias yet. Narrowing that binding is a tracked follow-up.

## `scripts/gate.mjs`: one local gate for an exact commit
`node scripts/gate.mjs` runs the same list of checks as CI and the production build script (unit tests, rules, release-output tests, release coverage, production build, served checks, browser, PWA, practice, mock exam, papers, final prep, figures) plus the snapshot check, then prints one table with the commit and tree. `--fast` runs only the unit, rules and coverage steps; `--only a,b` picks steps; `--list` prints them. It never refreshes the snapshot: a stale snapshot fails with the command to run, because refreshing automatically would make the check pass by rewriting its own evidence. It is parity by step list, not by environment: CI also runs `npm ci` and `npm run setup:rules` first, while the gate assumes dependencies are installed. Like CI it records `src/content` byte hashes before the steps and checks them after, and fails if a step changed content. It does not write anything to make a check pass. Logs go to `/tmp/gate-logs`. A partial run says so and warns when tracked files differ from HEAD.

## `scripts/lib/load-styles.mjs`: stylesheets for fixtures
Browser fixtures that inline CSS must call `loadStyles(root)`. It reads the stylesheets the source imports: `main.jsx` first, then every other `.js/.jsx/.mjs` file under `src/` (not `src/content`), for `import './x.css'` and `import name from './x.css'`. Anything it cannot resolve (dynamic or `require` css, a `?inline` suffix, a missing file, a css `@import`) throws instead of being skipped. It does not run Vite, so it matches production by import discovery, not by Vite's chunk order. A test forbids naming a stylesheet in a fixture by hand and covers the throwing forms.
